# Known gaps

Everything here is a place where the code and the intent disagree: features described but not built, code that exists but is unused, and behaviour that is wrong on purpose for now. It exists so that neither the next reader nor an agent builds on something that isn't there.

Last audited against the code on 2026-09-28 (the database now has separate `form_ai_migrator` and `form_ai_app` roles, and the deploy pipeline applies migrations as a one-off ECS task before each rollout, though that path has not yet run against real AWS — see [ADR 0007](./adr/0007-migrations-run-as-a-separate-role-in-a-deploy-job.md); a `RefreshTokenCleanupWorker` now runs daily inside `FormAI.API` and bulk-deletes revoked or expired `refresh_tokens` rows once they've been inactive for `RefreshTokenCleanup:RetentionDays` (default 10 days) — see `docs/plans/phase-36.md`); on 2026-09-27 (refresh tokens now live in an `HttpOnly` cookie, are stored hashed, and rotate on every use — see [ADR 0006](./adr/0006-refresh-token-httponly-cookie.md)); on 2026-09-25 `POST /api/forms/generate/text` is now rate limited per user with a sliding window, but only in the memory of a single server, and its `SourceText` is capped at 30,000 characters; on 2026-09-24 `ShowResultsAfterSubmit` is now chosen by the owner and gates the score returned by `POST {id}/submit`; on 2026-09-14 the Results tab now has an Individual sub-tab, so the individual-submission endpoints are called from the frontend, not just the backend; `FormAccessValidator` still centralizes every access check into `CheckOwnerAccess` and `CheckUserAnswerAccess`; every check in the app answers 404, never 403; the owner can no longer answer or read their own private/expired form through the answering path).

## Not built

| Feature                                     | What actually exists                                                                                                                                                                                                                                                               |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Result analysis by AI**                   | `IAnalysisService` and `AnalysisResult` are declared in `Application/AI/`. There is no implementation, no registration and no endpoint. The README used to promise this.                                                                                                           |
| **Generation from PDF, Word, image or URL** | Only `POST /api/forms/generate/text` exists. `PdfExtractor` and `UrlScraper` are unreferenced classes that throw `NotImplementedException`. `GenerateFormRequest` accepts `SourceType` and `SourceUrl`, but `GenerateFormHandler` hardcodes `SourceType.Text` and ignores the URL. |
| **Multiple source items per form**          | `FormSourceContent` is a list and `GenerateFormHandler.CombineItems` can merge several sources, but generation always builds exactly one item from `SourceText`.                                                                                                                   |

## Wrong or incomplete on purpose

| Behaviour                                           | Detail                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Expired unconfirmed accounts are never cleaned up** | The confirmation token expires after 15 minutes (`User.PendingRegistrationExpiresAt`). A user who misses it can ask for a new one (`POST /api/auth/resend-verification`, from the register success page), but only while that page still holds their email in router state — a refresh or a later visit has no resend, and there is no resend on the login page. There is no cleanup of expired unconfirmed users, so abandoned rows accumulate and keep their email taken. Accounts created before login enforced confirmation are locked out until they confirm. |
| **Demo accounts are never cleaned up**              | Every click on "Try demo" (`POST /api/auth/demo`) creates a real `users` row flagged `IsDemo`, with its forms and submissions. Nothing deletes them yet: the planned background service will delete demo accounts by age, and their forms go with them through the cascade. Until it exists the rows accumulate, and the banner's "1 day" is a promise nothing keeps — a demo user's forms keep the expiry they were given. |
| **Generation rate limit holds for one server only** | `POST /api/forms/generate/text` is limited per user with ASP.NET Core's built-in sliding window (`RateLimiting:Generate`, default 10 per 60 minutes). The counters live in the API process's memory, so a restart resets them and N API instances allow N times the limit. Move them to Redis (already running for SignalR) or count recent forms in the database before running more than one instance. `POST /api/auth/resend-verification` is limited the same way (`RateLimiting:ResendVerification`, default 3 per 15 minutes, per IP since it is anonymous); login, register and `POST {id}/submit` are not. A 429 carries no `Retry-After` header, because a sliding window reports no retry time. The request body limit is still Kestrel's 30 MB default, so the 30,000-character `SourceText` cap is only checked after the body has been parsed. |
| **`GenerationBudgetReached` is never thrown** | The code is declared in `ValidationErrorCode` and the middleware maps it to 503, but nothing throws it until the monthly spend ceiling ships (phase-37, slice 7). |
| **Prompt-injection resistance is not measured** | The pasted text is fenced by a per-request random marker and the system prompt tells the model to treat it as untrusted data (`UntrustedSource`), and the strict response schema limits the shape of any reply. That is a mitigation, not a proof: no test shows a model ignores an instruction inside the text. The injection documents of phase-37 slice 17 are the check. |
| **Reading every submission at once is unbounded**   | Two reads have this shape, and both are deliberately named so they are easy to find: `ISubmissionRepository.GetByFormForScoringAsync` (tracked, so a grading-relevant editor save can rescore and commit) and `GetByFormWithAnswersAsync` (untracked and split-query, for the results view). Each loads every submission of the form with its answers and selected options. Fine at current sizes; the two call sites to revisit if a form ever collects thousands of submissions.                                                                                                                                                                                                                                               |
| **No refresh-token reuse detection**                | Rotation revokes the old token when a new one is issued, but nothing checks whether an already-revoked token is presented again — which is exactly what happens if a stolen refresh token is used after the legitimate client has already rotated past it. There is no alert and no cascading revocation of the rest of that token's family; a reused token is just rejected as expired/revoked, the same as any other invalid one. See [ADR 0006](./adr/0006-refresh-token-httponly-cookie.md).                                                                                                                                                                                                                          |
