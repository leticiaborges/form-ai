# Form results are pushed live via SignalR, fanned out through a Redis backplane

Before this, the owner's Results tab only refreshed when they manually reloaded the page or saved the form editor — a new submission never showed up on its own. This adds a push channel: `SubmitFormHandler` notifies a `FormResultsHub` after a submission is saved, the hub pushes a bare `ResultsUpdated(formId)` signal to whichever connections have joined that form's group, and the frontend responds by refetching through the existing, already-authorized `GET /api/forms/{id}/results` call. The hub never carries the computed `FormResults` payload itself — only the words "something changed here."

Three approaches were considered and rejected for the transport: short polling (no real push, just a smaller reload interval), Server-Sent Events with the same Redis backplane (identical fan-out problem to SignalR, but more hand-rolled plumbing for no benefit over a library that already solves it), and a fully AWS-native stack (API Gateway WebSocket + Lambda + DynamoDB for connection tracking + EventBridge). The AWS-native option is the most "cloud-native" answer, but it buys scaling that is independent of any single server's connection count — value this feature doesn't need. What's being notified here is, at most, one owner's one open browser tab per form; SignalR with a Redis backplane already scales to that comfortably once this project runs multiple API instances behind a load balancer, without adopting a second, heavier serverless architecture alongside the existing ASP.NET Core one.

The second decision is how the Hub connection authenticates. Every other endpoint in this API sends a JWT as an `Authorization: Bearer` header, but a browser's native WebSocket API has no way to set custom headers on the handshake request that opens a hub connection — there is no code path available to a browser-based SignalR client that could attach one. The token has to travel some other way, so it's appended as `?access_token=...` on the connection URL and read back out in `OnMessageReceived`, added to the *existing* `AddJwtBearer` configuration rather than a second auth scheme. That handler only honors the query-string token for paths under `/hubs`; every other endpoint still requires the real header. Once read, the token goes through the exact same signature/issuer/audience/lifetime validation as any other request — only where the token is read from changes, not how it's checked.

## Consequences

- **The hub's own access check (`JoinFormResults` → `FormAccessValidator.CheckOwnerAccess`) only gates group membership, not data.** The actual result content is still protected independently by `GetFormResultsHandler`'s own `CheckOwnerAccess` call on the REST endpoint the frontend refetches from. Removing the hub-side check wouldn't leak result data — it would let a non-owner learn that a given form id exists and is receiving submissions, which is why it's still required.
- **Redis is a pure pub/sub relay, not a queue.** A `PUBLISH` to a group with no current subscriber is simply dropped — there is no persistence, delivery guarantee, or replay. If the owner isn't watching when a submission lands, they see the correct data on their next visit via the ordinary REST fetch; they just don't get a live nudge for the update they missed. Correctness never depends on the push arriving.
- **The backplane is inert at the scale this project runs at today.** With a single API instance, `Clients.Group(...)` would behave identically without `AddStackExchangeRedis`. It exists solely for the documented future requirement of running multiple instances behind a load balancer, where `Clients.Group(...)` on one instance otherwise cannot reach a connection held by another.
- **Group membership lives on the connection, not the user, and does not survive a reconnect.** A dropped connection that reconnects gets a new `ConnectionId` with no memory of its prior group membership, so the client must explicitly rejoin (`onreconnected` → `JoinFormResults`) every time. This is also what makes a rolling deploy or an instance being scaled in transparent to the owner, once the load balancer and ECS/ASG settings are tuned for it.
- **Query-string tokens are exposed to anything that logs full request URLs** — reverse proxies, API gateways, and access logs more commonly capture query strings than headers. This is scoped as narrowly as possible (`/hubs` paths only) and bounded by the short lifetime of the access token in the existing refresh-token flow, but it is a real, accepted trade-off, not a non-issue.
- **No automated test exercises the hub's authorization or the Redis fan-out.** Both require genuine multi-connection, and eventually multi-instance, verification that isn't practical as a unit or integration test; `SubmitFormHandler`'s obligation to call the notifier is unit-tested via a fake (`RecordingFormResultsNotifier`), which is as far as the automated suite goes.

## Status

Accepted and implemented — `FormResultsHub`, `SignalRFormResultsNotifier`, and `IFormResultsClient` in `FormAI.API/Hubs/`, and `useFormResultsHub` on the frontend.
