# Migrations run as a separate database role in a deploy-time job, never at API startup

The database has two login roles. `form_ai_migrator` owns the database and its `public` schema and is the only role that runs DDL. `form_ai_app` is what the API connects as; it gets `SELECT`, `INSERT`, `UPDATE` and `DELETE` on tables and `USAGE` on sequences, and nothing else — it cannot create, alter, drop or truncate. Grants reach new tables automatically through `ALTER DEFAULT PRIVILEGES FOR ROLE form_ai_migrator`, so a migration never has to grant anything. Migrations are applied by the deploy pipeline as a one-off job before the new API version rolls out; the API never calls `Migrate()`.

Alternatives considered:

- **`Migrate()` at startup.** The simplest option, and since EF Core 9 it takes a database-wide lock, so racing instances are no longer the problem. It was rejected because the API would need DDL rights, and because a failing migration would fail every new instance at once instead of stopping the deploy before any instance changes. The EF Core docs prefer a separate deployment step when "least-privilege credentials, coordinated rollout, or high availability is important".
- **Running migrations as the RDS master user.** One fewer role and secret, but every deploy would carry `rds_superuser` credentials and every table would be owned by the master, which is painful to undo later. The master (`form_ai_admin`) is used only once, to create the two roles.
- **A `NOLOGIN` owner role with the migrator as a member.** Common in larger setups so credentials can rotate without reassigning ownership. It adds a role for something already achieved here: rotation is `ALTER ROLE ... PASSWORD` on the same role, which the bootstrap script does on every run.

The roles are created by one idempotent script, `docker/postgres/init/01-create-app-user.sh`, used unchanged by Docker's first-start init, by CI and, in production, by a one-off ECS task. RDS is in private subnets, so nothing outside the VPC can run SQL against it; the bootstrap and the migrations both run as Fargate tasks in the ECS tasks' security group, started with `aws ecs run-task`.

## Consequences

- **Migrations must work with the previous release of the app.** The migrate job runs before the rollout, so old instances keep serving traffic against the new schema for a while. Add columns as nullable or with a default; drop or rename in a later release, once nothing reads the old shape.
- **`dotnet ef database update` needs `--connection` as `form_ai_migrator`.** The role in the API's connection string cannot change the schema, so running it without the flag fails on purpose.
- **The automatic grants only cover objects `form_ai_migrator` creates.** A table created by any other role (a superuser fixing something by hand) is invisible to the API until someone grants on it.
- **A failed migration stops the deploy.** The pipeline waits for the task and aborts on a non-zero exit, so no instance is replaced. There is no automatic rollback; a bad migration needs a follow-up migration.
- **The role passwords live in Terraform state.** They are generated by `random_password` and stored in Secrets Manager, in two secrets: the API's execution role can read only the one with the `form_ai_app` connection string, never the migrator's. Rotating one means replacing the `random_password`, applying, and re-running the bootstrap task; instances that started in between keep the old value until they restart.
- **The EF tools and the bundle create the context through `AppDbContextFactory`, not through the API host.** Booting `Program.cs` throws without `ConnectionStrings:Redis` (checked: that is what stops the tools today; the `Jwt` checks in `AddInfrastructure` do not, because `appsettings.json` supplies a `Jwt` section), so the migrate job would carry placeholder settings and break whenever the host gains a new required one. Those startup checks stay: failing fast at API startup is what we want there. The factory and `AddInfrastructure` both take their options from `AppDbContextOptions.UseAppDatabase`, so the model the tools see cannot drift from the one the API runs; only the connection string differs (a placeholder in the factory, since `--connection` supplies the real one).
- **Production needs a manual step after the database is created.** The bootstrap task is run by hand with an admin's own AWS credentials; the deploy role is deliberately not allowed to start it.

## Status

Accepted and implemented, apart from what is untested against real AWS. The two roles and the shared script; the CI end-to-end job (roles created, migrations applied as the migrator, API run as `form_ai_app`); the Terraform for the secrets, the `db-bootstrap` and `db-migrate` task definitions, their execution role and the deploy role's permissions; the migrator image (`src/FormAI.Infrastructure/Dockerfile.migrator`, an EF Core bundle) and the migrate step in `deploy.yml`, which registers a revision of the `db-migrate` task with the build's image, runs it in the API service's own subnets and security group, and stops the deploy on a non-zero exit. The image was run locally against PostgreSQL 18 bootstrapped with the real script: it applied every migration as `form_ai_migrator`, was a no-op the second time, failed on a wrong password, and failed as `form_ai_app`, which is refused `CREATE` on the schema. The bootstrap task and the deploy step have not run against a real RDS instance or AWS account; the bootstrap script was tested with a non-superuser admin standing in for the RDS master.
